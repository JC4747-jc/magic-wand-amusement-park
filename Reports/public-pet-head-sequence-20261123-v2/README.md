# 萌宠连续片段与头位挂接

## 犬连续片段

从缓存的 Total-Recon 犬原片选 5 段共 122 帧，复用 44 个已校正帧，从已核对的归档前缀补齐其余 78 帧。每帧使用实际左右图与共同双目标定。左图以软件 JPEG 90 经真实 PICF v2 与正式 YOLOv8n 推理，右图按 PICO 代码生成灰度。逐帧用原生双目算法复算身体位置，再以相同的鼻眼和双向纹理条件检查头位。

| 项目 | 帧数 |
| --- | ---: |
| 原片 | 122 |
| 有唯一高置信犬框 | 121 |
| 身体测距通过 | 55 |
| 鼻眼和纹理门槛通过 | 7 |

分别按源帧间隔 1、2、3 检查同一 ID，身体确认前要求连续三帧相邻位置差不超过 12 cm，身体确认后使用 45 cm 跳变门槛。缺失的帧保留为中断。五段均没有身体确认和连续三个头位候选同时满足的片段。此筛查不计算 Unity 平滑后的真实跟踪状态，且使用软件编码和离线节奏。犬头鼻尖缺少独立有效 LiDAR 深度，仍需不同个体的公制数据。

本轮没有新增网络下载。定向展开与校正数据约 231 MiB，最低采样可用 RAM 7.38 GiB，进程组最高采样约 939 MiB，资源保护未触发。[数据来源](https://github.com/andrewsonga/Total-Recon#data) · [逐帧结果](result.json) · [输入清单](input.json) · [资源采样](resources.json)

## 猫候选：Unity 挂接、超时和恢复

保存的 BridgeStereoFusion 进入 ParkPet 后，用原发送器和接收器传递 9 条真实 PICF 回包。PC 使用已核对的本地 YOLO11s 猫候选与 AP-10K，逐条绑定实际 Unity JPEG、右灰度、帧号、时间戳和实例 ID。Unity Editor 试验代码在原身体确认通过后更新头位，桌面提供位姿。猫源帧 30–32 连续三帧使同一实例建立头位，候选距离 1.476 米，左目 LiDAR 鼻尖附近约 1.537 米。

- 七条正常空间回包耗时 251–295 ms。故意延迟后，第五条回包在 641 ms 到达，原接收器只保留识别，候选头位清除。
- 恢复后的同一 ID 必须再通过三次新观测，然后重新挂接头位。随后切到录像另一段，PC 分配新 ID，旧头位清除，新实例在只有一次观测时未取得头位。
- 首轮试验的末帧曾被软件 JPEG 回放预测为不可用，实际 Unity JPEG 产生可用头部证据和新 ID。复试将它用于 ID 切换。独立背脸测试沿用既有结果。

本次通过的是 Editor 试验模式的候选头位生命周期。正式 PC 权重、Android 包和场景配置未改，PICO 真机和真实手势未验。Unity 与 PC 运行最低采样可用 RAM 5.75 GiB，候选盘最大采样净增 0 MiB。[实际轨迹](live-cat/trace.txt) · [原 PICF 回包](live-cat/live-picf-replies.jsonl) · [资源采样](live-cat/unity-resources.json) · [来源与哈希](verification.json)
